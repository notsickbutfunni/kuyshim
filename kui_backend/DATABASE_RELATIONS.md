# Связи Базы Данных (Database Relations): Архитектура Kuyshim

В этом документе подробно описаны все связи (relations) между таблицами в вашей базе данных PostgreSQL. База данных спроектирована по принципам реляционной архитектуры, что означает, что данные не дублируются, а ссылаются друг на друга с помощью **внешних ключей (Foreign Keys)**.

---

## 1. Главные Сущности (Родительские таблицы)

Эти две таблицы являются "ядром" системы. От них зависят все остальные данные.

### Таблица `users` (Пользователи)
* **Что сохраняет:** Учетные данные пользователя (Имя, Email, Хешированный пароль, Ссылка на аватарку).
* **Связи:** Один пользователь может иметь множество оценок, множество записей прогресса и множество достижений (Связь **One-to-Many** / Один-ко-Многим).

### Таблица `kuis` (Кюи / Музыкальные произведения)
* **Что сохраняет:** Метаданные самого произведения (Название, Автор, Ссылка на аудио, BPM, Длительность, Общее количество нот, Уровень сложности).
* **Связи:** Один Кюй может иметь несколько уроков (Связь **One-to-Many**). *В текущей архитектуре к одному кюю привязан один урок, но структура позволяет в будущем добавить к одному произведению несколько уроков разной сложности.*

---

## 2. Зависимые Сущности (Дочерние таблицы)

Эти таблицы содержат `Foreign Key` (внешние ключи), которые ссылаются на родительские таблицы.

### Таблица `lessons` (Уроки)
* **Что сохраняет:** Образовательный контент для кюя (Текст урока, Ссылка на табы, Ссылка на обучающее видео).
* **Как связана:**
  * Содержит `kui_id` — ссылается на таблицу `kuis`. Без кюя урок существовать не может.
* **Связи:** Один урок может быть пройден множеством пользователей (Связь с таблицами `user_progress` и `performances`).

---

## 3. Сущности Взаимодействия (Связующие таблицы)

Эти таблицы связывают Пользователей (`users`) с Контентом (`lessons` или действиями).

### Таблица `user_progress` (Общий прогресс)
* **Что сохраняет:** Текущий статус пользователя по отношению к уроку (Начат `started` или Завершен `completed`). Это глобальное состояние (открыт уровень или нет).
* **Как связана:**
  * Содержит `user_id` — ссылается на `users`.
  * Содержит `lesson_id` — ссылается на `lessons`.
* **Тип связи:** Это классическая таблица-мост (Junction Table) для связи **Many-to-Many** (Многие-ко-Многим). Многие пользователи проходят многие уроки.

### Таблица `performances` (Детальная аналитика игры)
* **Что сохраняет:** Результат **каждой отдельной** попытки сыграть урок (Точность попадания в ноты, Отклонение от ритма, Итоговый балл, Дата и время игры).
* **Как связана:**
  * Содержит `user_id` — кто играл.
  * Содержит `lesson_id` — что играли.
* **Отличие от `user_progress`:** Если пользователь сыграет один урок 10 раз, в `user_progress` будет только 1 запись (Статус: Завершен), а в `performances` будет 10 записей. Это позволяет строить графики прогресса и отслеживать ежедневную активность (Activity Tracker).

### Таблица `user_achievements` (Достижения)
* **Что сохраняет:** Перманентно разблокированные значки/достижения (Например: "Тәй-тәй", "Күйші") и точную дату их получения (`unlocked_at`).
* **Как связана:**
  * Содержит `user_id` — какому пользователю принадлежит достижение.
* **Связь:** **One-to-Many** (Один пользователь -> Много достижений). Логика бэкенда выдает достижение, анализируя таблицу `user_progress` (считает количество завершенных уроков).

### Таблица `tuner_results` (Использование ML-тюнера)
* **Что сохраняет:** Результат работы нейросети (Распознанный аккорд, Уверенность нейросети `confidence`, Точное время).
* **Как связана:**
  * Содержит `user_id` — кто использовал тюнер.
* **Связь:** **One-to-Many** (Один пользователь -> Много использований тюнера).

---

## 4. Каскадное удаление (ON DELETE CASCADE)

Важная архитектурная особенность базы данных Kuyshim: **Все внешние ключи настроены на каскадное удаление (`ON DELETE CASCADE`)**.

**Что это значит и почему это важно:**
Если администратор удаляет `kui` из базы данных, SQL-сервер автоматически удалит:
1. Привязанный `lesson`.
2. Все записи `user_progress`, связанные с этим уроком.
3. Все `performances` (игровые сессии), связанные с этим уроком.

Точно так же, если удалить `user` (пользователя), база данных мгновенно удалит все его игровые сессии, достижения и использование тюнера.
*Это предотвращает появление "осиротевших" данных (Orphan Data) и защищает базу данных от переполнения мусором.*
