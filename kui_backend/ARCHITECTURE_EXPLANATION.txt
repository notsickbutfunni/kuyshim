================================================================================
KUYSHIM BACKEND ARCHITECTURE & DATABASE EXPLANATION (THE "WHY")
================================================================================
This document provides a deep dive into the reasoning behind the architectural 
choices in the Kuyshim backend. It is designed to help defend these decisions 
during a diploma presentation.

--------------------------------------------------------------------------------
1. THE CORE TECH STACK: WHY FASTAPI AND PYTHON?
--------------------------------------------------------------------------------
Your backend is built using Python and the FastAPI framework. 

* Why Python? 
Your app relies heavily on Machine Learning (specifically PyTorch and torchaudio 
for the chord recognition tuner). Python is the absolute industry standard for ML. 
By writing the backend in Python, you eliminate the need to bridge different 
languages (e.g., trying to run Python ML scripts from a Node.js or Java server). 
Everything exists in a single, cohesive ecosystem.

* Why FastAPI? 
FastAPI is built on modern asynchronous Python (async/await). It is exceptionally 
fast—comparable to NodeJS or Go.
  - Automatic Documentation: FastAPI automatically generates Swagger UI 
    documentation based on your code. You do not have to manually write API docs.
  - Built-in Validation: It uses a library called Pydantic. If the mobile app 
    sends incorrect data (like a string instead of a number for a score), the 
    server automatically rejects it with a clear error before it even reaches 
    your logic, preventing server crashes and corrupted data.

--------------------------------------------------------------------------------
2. THE DATABASE CHOICE: WHY POSTGRESQL & SQLALCHEMY?
--------------------------------------------------------------------------------
You are using a relational database (PostgreSQL via Docker), managed by the 
SQLAlchemy ORM.

* Why Relational (SQL)? 
Your data is highly structured and connected. A user *has* performances, a lesson 
*belongs* to a kui. Relational databases enforce these rules using Foreign Keys, 
ensuring data integrity (e.g., it is impossible to have a progress record for a 
user or a lesson that doesn't exist).

* Why PostgreSQL? 
It is the most robust, enterprise-grade open-source relational database. It 
handles concurrent connections gracefully, which is essential if multiple users 
are playing the rhythm game and submitting scores simultaneously.

* Why SQLAlchemy (ORM)? 
It acts as a translator. Instead of writing raw SQL queries as text (which is 
vulnerable to SQL injection attacks), you interact with the database using Python 
objects. This makes the code safer, easier to maintain, and allows you to swap 
databases (like using SQLite for quick local testing and Postgres for production) 
without rewriting a single query.

--------------------------------------------------------------------------------
3. DATABASE SCHEMA: THE "WHY" BEHIND THE TABLES
--------------------------------------------------------------------------------

[ The 'users' Table ]
Columns: id, username, email, hashed_password, avatar_url.
* Why 'hashed_password'? 
  You never store plain-text passwords. You use the bcrypt algorithm via passlib. 
  If your database is ever compromised, hackers only get a mathematical hash, 
  not the actual passwords.
* Why 'avatar_url' instead of storing the image directly in the database? 
  Storing raw binary image data (BLOBs) inside a database makes the database 
  massive, slow, and expensive to backup. Instead, you save the image to your 
  server's file system (storage/avatars) and only save the *text URL* pointing 
  to that file in the database. This is an industry best practice.

[ The 'kuis' and 'lessons' Tables ]
* Why are they separate? 
  A 'kui' (e.g., "Adai") is the musical composition. It has a BPM, duration, and 
  the raw audio. A 'lesson' is the educational material built *around* that 
  composition. By separating them, you could theoretically create multiple 
  lessons (e.g., "Adai for Beginners", "Adai Masterclass") that all point to 
  the exact same single audio file. This prevents data duplication and saves 
  storage space.

[ The 'user_progress' vs. 'performances' Tables ]
* Why two tables for tracking progress? 
  This is a crucial architectural decision for your rhythm game.
  - 'user_progress' tracks the global state (started, completed) and the overall 
    highest score. It quickly answers the question: "Has this user unlocked the 
    next level?"
  - 'performances' is an analytical ledger. Every single time a user plays a 
    song, a new row is inserted with their exact accuracy, timing offset, and 
    note consistency. This allows you to generate historical charts (e.g., 
    showing the user how their accuracy has improved over the last 30 days) 
    without overwriting their best score.

[ The 'tuner_results' Table ]
* Why store tuner results?
  Machine Learning models need real-world data to improve. By storing the 
  predicted chord and the model's confidence score, you are creating a dataset. 
  In the future, you can analyze this table to see which chords users struggle 
  with the most, or identify if the ML model consistently has low confidence 
  on a specific note, indicating that the model needs retraining.

--------------------------------------------------------------------------------
4. SECURITY & DEPLOYMENT: THE "WHY"
--------------------------------------------------------------------------------
* Why JWT (JSON Web Tokens) for Authentication?
  JWTs are stateless. When a user logs in, the server gives them a token. For 
  subsequent requests, the user sends the token. The server doesn't need to look 
  up a session in the database to verify the user; it simply verifies the 
  cryptographic signature of the token. This makes your API incredibly fast and 
  scalable.

* Why Docker?
  "It works on my machine" is a common problem in software development. By 
  putting your FastAPI backend and PostgreSQL database inside Docker containers, 
  you guarantee that the exact same environment (Python version, system libraries, 
  database version) is used in development, testing, and production.
